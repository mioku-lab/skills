# Build and verify

## Commands

```bash
bun run build        # loops packages/*/ and runs tsdown in each
bun run dev          # packages/mioku in watch mode
bun run typecheck    # bunx tsc --noEmit over the whole workspace
bun run start        # boots example/
bun run docs:dev     # typedoc then vitepress dev
bun run docs:build   # typedoc then vitepress build
```

The root `build` script only descends into a package that has a `src/` directory or a
`tsdown.config.ts`, so adding a config file is what makes a new package buildable.

## There is no test suite

This repository has **no unit tests and no test runner**. Do not invent a framework or add
a test dependency without agreeing on it first — that is an architectural decision.

Correctness is established by running the framework. Two levels:

### 1. Typecheck and load

```bash
bun run typecheck
```

Then boot and read the log:

```bash
bun run start
```

A plugin or adapter that fails validation says so at load with a specific message
(`Plugin canonical ID mismatch`, `invalid: missing init()`, `apiVersion mismatch`). Confirm
your change appears in the startup log at all — silence usually means discovery rejected it.

### 2. Reproduce the behaviour through the stdin adapter

`mioku-adapter-stdin` turns standard input lines into private messages, so a full
end-to-end path works with no QQ account:

```
mioku> .hello
你好呀，世界
```

That exercises the real pipeline — command manager, permissions, bus, capability binding,
reply — which is exactly the path most core changes affect.

For anything involving real platform behaviour (media segments, poke events, multi-account
dedup), use the `example/` project with its configured adapters. `example/package.json`
links every workspace package with `workspace:*`, so a framework change is picked up by a
restart without publishing.

## Verification recipe for a core change

1. State the observable behaviour that should change.
2. Reproduce it **before** the change and capture the output.
3. Make the change.
4. `bun run typecheck`.
5. Reproduce again; diff the output.
6. Check the negative path too — the error or edge case the change was meant to fix usually
   has a neighbouring case you can break.
7. Check the startup log for new warnings from the loader.

Do not report a core change as verified on the strength of a typecheck alone. Typechecking
proves the shape, not the ordering, which is where most core bugs live.

## When the change is behavioural, name the invariant

Before editing the runtime, loader or bus, write down which invariant from the core skill
you are touching — ordering, dedup ownership, projection safety, shutdown budget,
`apiVersion` gating. Most regressions here are a violated invariant that still compiles.

## Documentation

`docs/reference/api` is generated by typedoc from source. When you change a public type:

```bash
bun run docs:dev     # regenerates typedoc output, then serves the site
```

Hand-written docs live in `docs/guide`, `docs/developer` and `docs/advanced`. If a change
contradicts one of them, update the doc in the same change — the developer docs are the
manual users read, and drift there is worse than no docs.

Known drift to fix if you touch the area: the configuration doc lists a `fatal` log level
that does not exist and omits `silent` and `log`.

## Adding a new package

1. Create `packages/mioku-<kind>-<short>/` with `package.json`, `tsconfig.json`,
   `tsdown.config.ts`, `src/` (or a root `index.ts` for a plugin/service/adapter), a
   `README.md`, and `config.md` if it takes config.
2. Name it with the right prefix — the loader classifies purely on the prefix.
3. Add it to `example/package.json` as `workspace:*` and enable it, so it is exercised.
4. Add an entry to `official-registry.json` under `plugins` / `services` / `adapters` with
   its npm name, otherwise it is not installable from the market.
5. `bun run build` and confirm the package is picked up by the loop.

## Version bumps

Bumping is a judgement call, not a reflex. `mioku-code-style/references/change-management.md`
has the full rule: one bump per finished, consumer-visible change; never per edit; never
while the user has not committed and the work is still the same feature. When the change is
a breaking interface change, the bump is mandatory and so is saying so in the report.
